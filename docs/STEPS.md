# Steps

1. Schema first: boards, members, notes, votes, with the `(board_id, col, pos)` index the board load leans on and `CHECK` constraints on columns and vote counts.
2. Identity without signup: create a board and get an owner session; join with an invite token and a display name and get a guest session. Random 32-byte tokens, only their sha256 stored. Per-IP rate limits on create/join.
3. Message validation (`validate.js`): a schema per message type, exact key sets, size and range limits, control and bidi characters stripped. Written before any handler so no handler ever sees unvalidated input.
4. WebSocket server: Origin check on upgrade, first-message auth with a 5s deadline, 4 KB frame cap, text only, per-connection token bucket, heartbeat, connection caps.
5. Server-assigned timestamps: `nextTs()` is strictly increasing per board; notes carry separate `text_ts` and `pos_ts`. Last write wins, decided by arrival order at the server.
6. Events are published raw on a bus and rendered per client. This is where anonymous mode is enforced (authors stripped on the server) and where `own` and a voter's private `remaining` get attached.
7. Dot-voting: the limit check and the write happen in one `BEGIN IMMEDIATE` transaction. Taking back the last vote deletes the row.
8. Timer: owner starts it, the server stores `timer_end` and broadcasts `{endsAt, serverNow}`; clients compute their clock offset and count down locally. Late joiners get it in the snapshot.
9. Export: authenticated `GET`, Markdown with note text escaped and flattened, authors omitted in anonymous mode.
10. Client: vanilla JS, `textContent` only, strict CSP. Keyed DOM updates, HTML5 drag and drop with fractional positions, cursors throttled to 25/s, reconnect with backoff and jitter, offline drafts re-sent after the snapshot.
11. Tests: 21 against a real server and real sockets, then a manual two-user pass in Chrome including a server restart mid-session.

# Interview Q&A

**1. How do you authenticate a WebSocket?**
The browser WebSocket API can't set an `Authorization` header, and putting a token in the URL leaks it into logs and proxies. So the HTTP join step issues a random session token and the first WebSocket message must be `{t:'auth', session}`; until it arrives (within 5s) the only accepted message is `auth`, anything else closes the socket. The server stores only `sha256(token)`. On upgrade I also check that `Origin` matches `Host`. That matters most with cookie auth (cross-site WebSocket hijacking); with a bearer token it's defense in depth, and non-browser clients that send no Origin are still allowed. Weak spots: the token lives in `localStorage`, so an XSS would steal it, and sessions never expire. A production version would add expiry and rotation, and `wss://` only.

**2. Last-write-wins or CRDTs for conflict resolution?**
LWW here, deliberately. The conflicts that can happen are small: two people dragging the same note, or one author editing in two tabs. Text edits are author-only, so the only real concurrent text writers are one person's own devices. The server stamps every write with a strictly increasing timestamp and the last to arrive wins; clients drop any update older than what they hold, so reordering can't regress state. Text and position have separate timestamps so a move can't clobber an edit. The cost is that concurrent edits to the same text lose one side entirely. If notes were shared documents, where two people type into the same text at once, I'd use a CRDT such as Yjs, which merges character-level edits instead of picking a winner. The price is metadata growth, tombstones, and a heavier protocol. For sticky notes that's overkill. One more LWW caveat: with several server nodes, `Date.now()` clocks differ, so the timestamp would have to come from the database or a shared counter.

**3. How do you handle reconnects?**
Client: exponential backoff (500ms doubling, capped at 15s) with jitter so a server restart doesn't get a thundering herd, plus an immediate retry on the browser's `online` and tab-visible events. On reconnect it authenticates again and the server sends a full snapshot (notes, my votes, remaining votes, timer, presence), which replaces local state. Edits typed while offline are kept as drafts and re-sent after the snapshot, and the author's draft wins. There's no replay of missed events, because a full snapshot of at most 300 small notes is simpler and can't have gaps. Drag moves made while offline are refused with a toast rather than queued, since the board may have moved on. The one close code that doesn't retry is 4001 (bad session). I tested a mid-session server kill and restart: both clients recovered with their state.

**4. How would you scale this with Redis pub/sub?**
Fan-out is already behind a `subscribe/publish` interface with events that are the same for every recipient. A Redis bus would `SUBSCRIBE board:<id>` when the first local socket joins a board and `PUBLISH` raw events; each node renders them for its own connections. The writes already go through SQLite/Postgres before publishing. What does not carry over yet: presence (it's computed from local sockets, so it needs a shared set with TTLs), the per-board timestamp counter (needs the database or Redis `INCR`), the in-memory IP limiters (move to Redis), and SQLite itself (one writer, one machine, so move to Postgres). Sockets don't need sticky sessions since any node can serve any board. Cursors are the volume problem: they're high-frequency and ephemeral, so I'd consider keeping them off Redis, or coalescing them per board per tick.

**5. How do you stop XSS in user notes?**
Layers. (1) The client never uses `innerHTML`; every piece of user text goes through `textContent` or text nodes, so `<img onerror=...>` renders as literal characters (I checked this in a browser). (2) A strict CSP: `script-src 'self'`, no inline script, `default-src 'none'`, so an injection bug elsewhere still can't run inline code or load remote scripts, and `connect-src 'self'` limits exfiltration. (3) Input is validated and stripped of control and bidi-override characters, with length limits, but I deliberately don't HTML-escape on the way in: the stored data stays raw and escaping happens at the output, per context. (4) The Markdown export is another output context, so note text is flattened to one line and inline syntax is escaped, otherwise a note could inject a heading or link into someone's document. The remaining risk is the session in `localStorage`; an httpOnly cookie would take it out of script reach but brings CSRF back into play.

**6. How is rate limiting done, and what does it miss?**
Three levels. HTTP: per-IP token buckets on board creation and join/invite lookup (in memory). WebSocket: a token bucket per connection (burst 60, 40/s), where excess messages are dropped with an error and 50 violations closes the socket; plus a 4 KB frame limit, 500-char note limit, 300 notes per board, 50 members per board, and 5 sockets per member. A token bucket allows short bursts, which suits cursor movement and rapid typing, and bounds the long-run rate. What it misses: it's per connection, so someone can open many connections (the per-member and per-board caps blunt that, but a determined abuser can create many guest members, only slowed by the per-IP join limit). It's in memory, so it resets on restart and doesn't span processes. Behind a proxy `req.ip` would be the proxy unless `trust proxy` is configured. And it's no substitute for a network-level limiter in front.
